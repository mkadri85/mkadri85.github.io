My team runs a production marketplace platform: a Node and Next.js monorepo, a React admin console, a Flutter app, all deploying straight to live on every merge. Two developers, different machines, different AI coding assistants. I work mostly in Claude Code; my collaborator works in Cursor and Codex.

Git kept our code in sync. Nothing kept our understanding in sync.

Every assistant on every machine was building its own private model of the project inside its conversation history: which architectural approaches we had already rejected, why a payment flow is locked to one specific mode, which innocent-looking refactor causes a production incident. When the other developer opened his assistant, none of that existed. He re-explained the project from scratch, his agent proposed architectures mine had already rejected, and both of us kept rediscovering the same landmines.

The cost was not theoretical. Reviewing our own history, one class of authorization bug shipped six separate times in four months. Each time, the developer and agent who fixed it learned the lesson. The knowledge then evaporated into a chat log, and the next feature reintroduced the bug.

The Docker Compose insight

I kept telling my collaborator I wanted "something like Docker for AI context," and the analogy turned out to be exact, including its lesson.

Docker did not unify runtime environments by running a synchronization service. It unified them with a committed text file. docker-compose.yml travels with the repo, and every machine interprets it identically. The environment problem became a file-contract problem, and git solved the distribution for free.

AI project memory has the same shape. The missing piece is a file contract that every agent reads on session start and writes back to before session end. Git is already the bus, and no new infrastructure is required.

What the ecosystem offers (July 2026)

Before building, I surveyed what exists. Four things matter:

ApproachVerdict
AGENTS.md, the open instruction-file standard now stewarded under the Linux Foundation. Read natively by 20+ tools: Codex, Cursor, Copilot, Windsurf, Zed, Gemini CLI, Aider, Devin and more.Use it as the single entry point.
Claude Code does not read AGENTS.md natively (it is the most upvoted open feature request on its tracker), but CLAUDE.md supports imports. A one-line @AGENTS.md bridges it completely.Use the import; keep one canonical file.
The memory-bank pattern (popularized by Cline): a small committed directory of markdown the agent reads at start and updates at end. A methodology, not a product.Use the shape, trimmed hard.
MCP memory services (mem0 and friends): an always-on store with embeddings and semantic recall that every tool connects to.Defer. Below roughly five developers, flat files plus grep beat a service on cost, trust and inspectability.

The documented failure mode surprised me. Practitioner reports agree that shared AI memory rarely fails by forgetting. It fails by confidently remembering something that is no longer true: a renamed function, a reverted decision, a dead flag. An uncurated shared memory becomes a shared source of hallucination for the whole team. Every design choice below follows from this.

The design: three layers, all plain files

Layer 1: AGENTS.md. One canonical instruction file per repo: architecture notes, build and deploy rules, conventions, review criteria, and the session contract below. Every tool my collaborator uses reads it natively. Claude Code reads it through the import shim:

# CLAUDE.md (entire file)
@AGENTS.md

All project instructions live in AGENTS.md, the cross-tool
canonical file. Do not add instructions here.

Layer 2: the .ai/ directory. The evolving shared memory, versioned and PR-reviewed like code:

.ai/
  STATE.md         <- THE handoff. Current state, in-flight work,
                      next steps, open questions. Rewritten, never
                      appended. Capped at ~100 lines.
  INDEX.md         <- one line per file below
  architecture.md  <- how the system hangs together, and WHY
  conventions.md   <- evolving patterns not yet stable enough
                      for AGENTS.md
  known-issues.md  <- live landmines, each entry dated
  lessons.md       <- failures already paid for
  decisions/
    ADR-001-....md <- one decision per file, immutable once
    ADR-002-....md    accepted; superseded, never edited

Layer 3: personal. Machine paths, private preferences, credentials. Gitignored local files and each assistant's own memory. Never committed.

The session contract

Written into AGENTS.md, three imperative bullets. Long policy documents get ignored by every agent; short contracts get followed.

  1. Session start: read .ai/STATE.md, then .ai/INDEX.md. Open other files only when relevant. Never bulk-load the whole directory into context.
  2. During work: when you make a decision or hit a landmine, update the matching .ai/ file in the same branch as the code change. Decisions become a new ADR.
  3. Session end: rewrite STATE.md: done, in flight, next, risks, open questions. Five minutes, not an essay.

Enforcement is deliberately light. A Claude Code SessionStart hook injects STATE.md into every session automatically:

#!/bin/bash
# .claude/hooks/session-start-ai-memory.sh
STATE="$CLAUDE_PROJECT_DIR/.ai/STATE.md"
if [ -f "$STATE" ]; then
  echo "-- Shared project memory: .ai/STATE.md --"
  cat "$STATE"
  echo "-- Full index: .ai/INDEX.md. Rewrite STATE.md before finishing. --"
fi

For the other tools, AGENTS.md itself carries the instruction, and the PR template carries a checkbox: .ai/ updated (STATE.md / ADR / known-issues) or N/A. A reviewer treats a stale STATE.md like a failing test.

The anti-staleness contract

This is where these systems live or die, so it is non-negotiable:

  • Every claim is dated, and anything that cites code carries a warning that it is a point-in-time observation to re-verify.
  • Delete beats update beats append. Resolved issues are removed, not marked fixed and kept.
  • Memory changes ride the code PR and get the same review. A wrong memory entry is a bug that infects every future session of every developer.
  • Size caps force pruning: STATE.md under ~100 lines, topic files under ~150, the whole directory under ~15 files. Hitting a cap is the system working.
  • What never goes in: secrets, keys, personal data, anything derivable from code or git history, and raw chat transcripts. Summaries only; logs rot.

The gotcha that proved the point

Migrating the platform repo, our automated PR reviewer flagged something I had missed: the CI review script used CLAUDE.md as its project-context input. My change had just shrunk CLAUDE.md to a seven-line shim, which would have quietly lobotomized every future automated review.

The fix was one line (read AGENTS.md first, fall back to CLAUDE.md), plus adding AGENTS.md and .ai/** to the reviewer's watched paths, so changes to the shared memory itself now get reviewed like code. That last part is the whole discipline in miniature: the memory is a first-class artifact, and wrong memory is treated as seriously as wrong code.

Results and where the ceiling is

The migration took about half a day per repo, most of it seeding .ai/ from knowledge that previously lived in one assistant's private memory: the architecture map, a register of 24 known process gaps from a recent audit, and four ADRs recording decisions we had each re-litigated at least once. My collaborator installed nothing. His tools picked up AGENTS.md on the next pull, and his first session started with the full current state of my last one, including the exact blockers on his own open PRs.

The honest caveats:

  • The system is only as good as the STATE.md rewrite habit. The hook and the PR checkbox nudge; the immediate pain of a stale handoff is the real enforcement.
  • Agents treat instruction files as strong suggestions. Keeping the contract to three bullets is a feature, not laziness.
  • This is sized for a small team. My upgrade trigger is written down in advance: more than three developers, or the day grep across fifteen markdown files stops finding things. Then, and only then, an MCP memory service with semantic search earns its infrastructure.

Until that day, the shared brain is a directory of markdown, reviewed like code, distributed by git. The same boring trick that fixed environments a decade ago: commit the contract, not the machinery.
